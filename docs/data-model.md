# Data model

This document describes the data the tracker stores in its claude.ai Artifact database: the `applications` and `notifications` collections and the `settings/preferences`, `settings/schedule`, `settings/searchRequest` and `settings/emailImport` documents. For each one it lists every field, its type, its allowed values, and which part of the system reads or writes it (the page in `app/index.html`, or the hourly routine in `routines/hourly-check.md`).

## Overview

The database is the Artifact's built-in document store. The page opens it with `window.claude.use("db")` and listens for live changes with `onSnapshot`, so edits made by the routine appear on the page without a reload. The routine reads and writes it with the `ArtifactData` tool, acting as the artifact's owner.

| Path | Kind | Purpose |
| --- | --- | --- |
| `applications/<id>` | collection of documents | One document per job: listings, applications and skipped jobs. |
| `notifications/<id>` | collection of documents | Messages shown under the bell. |
| `settings/preferences` | single document | Search preferences for the listings task. |
| `settings/schedule` | single document | When the routine runs each task, plus the routine's URL. |
| `settings/searchRequest` | single document | The state of the latest **Find jobs now** request and the report of the latest listings run. |
| `settings/emailImport` | single document | Where the email import task got to and the result of its latest scan. |

In this document, "listings task", "import task", "reply checks" and "summary task" are the four tasks inside the hourly routine. The import task is "Import applications from email". See [Routines](routines.md).

Dates come in two formats:

- Date: `YYYY-MM-DD` string. The page uses the browser's local date. The routine uses the date in the `timezone` from `settings/schedule`.
- Timestamp: ISO 8601 string in UTC, for example `2026-10-12T01:30:00Z`.

## applications

Document IDs are generated by the database when the page adds a job (`col.add`) or when the listings task or the import task creates documents in a batch.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `company` | string | up to 120 chars in the form | page, listings task, import task | Shown as "Untitled" when empty. |
| `role` | string | up to 160 chars in the form | page, listings task, import task | |
| `location` | string | up to 120 chars in the form | page, listings task, import task | |
| `url` | string | `http` or `https` URL | page, listings task, import task | Other schemes are ignored by the page: no link is shown and Apply does not open anything. |
| `source` | string | up to 60 chars in the form | page, listings task, import task | Where the posting was found, such as a job board name. The import task uses the site the confirmation came from, for example `LinkedIn`, `Indeed`, `Greenhouse` or `Company site`. |
| `salary` | string | free text, up to 60 chars in the form | page, listings task, import task | As posted. Empty when not posted. |
| `match` | number or null | 0 to 100 | page, listings task, import task | Fit estimate. The page clamps form input to 0-100 and stores `null` when empty. The import task stores `null`. |
| `fit` | string | up to 600 chars in the form | page, listings task, import task | One or two sentences on why the job fits. A job added from a near miss gets `Near miss: <reason>`; the page uses this prefix to label the near miss "Added". |
| `contact` | string | up to 160 chars in the form | page, import task | Recruiter name or email. Reply checks use it to search Gmail. The import task fills it only when the confirmation came from a real person, never from a no-reply address, and otherwise leaves it empty. |
| `notes` | string | up to 4000 chars in the form | page, reply checks, import task | Reply checks prepend one dated line per reply and keep the rest. The import task writes `<YYYY-MM-DD> Imported from email: <subject>` on a new job, or prepends `<YYYY-MM-DD> Applied outside the tracker (from email: <subject>)` when it moves an existing job to `applied`. |
| `status` | string | see [Statuses](#statuses) | page, reply checks, listings task, import task | |
| `history` | array of objects | `{ status: string, date: Date }` | page, reply checks, listings task, import task | One entry appended per status change. The listings task creates it as `[]`. The import task creates it as `[{ status: "applied", date }]` with the email date, or appends that entry when it moves a job. |
| `dateFound` | Date | | page, listings task, import task | Set when the job is added. Shown as "Added" on listing cards. Listings are sorted newest first by this field. |
| `datePosted` | Date or null | | page, listings task, import task | Optional. The date shown on the original posting. The listings task omits it when the posting shows no date; the edit form stores `null` when empty, and the import task always stores `null`. Shown as "Posted" on listing cards, and used as the second sort key. |
| `dateApplied` | Date or null | | page, import task | Set to today when the job moves to `applied`, but only if it is empty. The import task sets it to the confirmation email's date in the schedule `timezone`, also only if it is empty. Editable in the form. Reply checks read it to set the start of their Gmail search, and the summary task reads it for "applied today" and follow-ups. |
| `followedUp` | Date | | page | Set by **Mark followed up**. Clears the follow-up reminder. Not shown in the edit form. |
| `lastUpdate` | Date | | page, all writers | Set on every write. Used as the last sort key. |
| `addedBy` | string | `user`, `claude`, `email` | page (`user`), listings task (`claude`), import task (`email`) | Jobs added from a near miss are `user`. The summary task counts only `claude` listings as "new listings added today". The import task sets `email` only on jobs it creates; it keeps the existing value when it moves a job. |
| `lastEmailCheck` | Timestamp | | reply checks | Time of the last Gmail check for this job. The next check searches from the later of this and `dateApplied`. |
| `emailMessageId` | string | Gmail message ID | import task | Optional. The confirmation email the job was imported from or matched to. The import task skips any email whose ID is already stored on a job. |
| `importedAt` | Date | | import task | Optional. The day the import task added the job or moved it to `applied`. The summary task lists jobs with `importedAt` equal to today. |

### Statuses

| Value | Label on the page | Where it appears | Set by |
| --- | --- | --- | --- |
| `listing` | Listing | Listings tab | listings task, page (Add job, Restore) |
| `applied` | Applied | Applied tab | page (Apply, status picker), import task |
| `responded` | Responded | Applied tab | page, reply checks |
| `interview` | Interview | Applied tab | page, reply checks |
| `offer` | Offer | Applied tab | page, reply checks |
| `rejected` | Rejected | Applied tab | page, reply checks |
| `ghosted` | No reply | Applied tab | page (status picker, **No reply** button on a follow-up) |
| `skipped` | Skipped | Skipped drawer | page (Skip) |

Legacy value: `found` is read as `listing`. A document with a missing or `found` status is shown as a listing. The page does not rewrite the stored value until the job is next changed.

Rules the page applies:

- The status picker in the Applied tab offers only `applied`, `responded`, `interview`, `offer`, `rejected` and `ghosted`. To move a job back to `listing` or to `skipped`, use the edit form.
- Moving a job to `applied`, whether with **Apply**, the status picker or the edit form, sets `dateApplied` to today only if it is empty. An existing `dateApplied` is never overwritten.
- **Undo** after Apply or Skip restores the previous `status` and `dateApplied` and removes the last `history` entry if it matches.
- A job counts as "applied" in the pipeline if its status is `applied`, `responded`, `interview`, `offer`, `rejected` or `ghosted`.
- A job counts as "responded" in the pipeline if its current status or any `history` entry is `responded`, `interview`, `offer` or `rejected`. "Interview" counts `interview` or `offer`. "Offer" counts `offer`. The response rate is responded divided by applied.
- A follow-up is due when `status` is `applied`, `followedUp` is not set, and `dateApplied` is 7 or more days ago.
- Listing cards are sorted by `dateFound`, then `datePosted`, then `lastUpdate`, newest first.
- When several listings are duplicates of each other (see [Duplicate keys](#duplicate-keys)), the Listings tab shows only the newest one, by `dateFound` then `lastUpdate`. The others stay in the database.
- **Add job** refuses to save a new job that duplicates any tracked job, in any status, and links to the existing one. Editing an existing job is not checked.
- The Applied table shows a small "From email" tag on a job whose `addedBy` is `email`, or that has an `importedAt` or `emailMessageId`.
- The edit form keeps `addedBy`, `emailMessageId` and `importedAt` when you save.

The summary task uses the same "applied", "responded" and response rate definitions, and reports the follow-ups the page shows as due as "overdue". It also lists follow-ups due tomorrow: the same conditions with `dateApplied` exactly 6 days ago.

The import task moves a job to `applied` only from `listing` (including a missing or legacy `found` status) or `skipped`. It never changes the status of a job that is already `applied`, `responded`, `interview`, `offer`, `rejected` or `ghosted`; it only fills an empty `emailMessageId` on it.

Reply checks cover jobs in `applied`, `responded`, `interview` and `ghosted`, so a reply to a job marked No reply moves it to `responded`, `interview`, `offer` or `rejected`. They never move a job backwards, for example from `interview` to `responded`.

### Duplicate keys

The page, the listings task and the import task use the same two keys. Two jobs are duplicates if either key matches.

- URL key: the posting URL's host without a leading `www.`, followed by its path without trailing slashes, all lowercased. The query string and hash are dropped. Jobs with no valid `http` or `https` URL have no URL key.
- Name key: `company|role`, each lowercased, with punctuation replaced by spaces and runs of whitespace collapsed. Jobs missing either the company or the role have no name key.

For example, `https://www.Example.com/jobs/123/?ref=feed` and `https://example.com/jobs/123` have the same URL key, `example.com/jobs/123`.

The listings task compares candidates against every job in `applications`, including `skipped` ones, and against candidates it already accepted in the same run. The import task does the same for each confirmation email: it compares against every job in `applications` and against jobs it already imported in the same run.

## notifications

The routine creates notifications. The page only marks them read.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `type` | string | `listing`, `reply`, `summary`, `import`, `status`, `info` | routine | Shown as "New listing", "Reply", "Daily summary", "Imported from email", "Status change", "Update". The current routine writes only `listing`, `reply`, `summary` and `import`. Unknown values show as "Update". |
| `text` | string | one sentence | routine | Shown as the notification text. |
| `jobId` | string | an `applications` document ID | reply checks | Optional. When set, selecting the notification jumps to that job. |
| `createdAt` | Timestamp | | routine | Used for sorting and the "2h ago" label. |
| `read` | boolean | | routine (`false`), page (`true`) | Unread notifications count toward the bell badge. |
| `lastUpdate` | Date | | page | Set when the page marks the notification read. |

Document IDs: reply checks use IDs like `reply-<jobId>-<yyyymmddhhmm>`. The listings, import and summary tasks let the database generate them. The import task creates at most one `import` notification per run, and only when it added or moved at least one job, for example "3 applications imported from email (1 moved from Listings)".

The bell shows all unread notifications under **New** and the 30 most recent read ones under **Earlier**. The badge counts unread notifications plus follow-ups due.

## settings/preferences

One document, written by the page's **Preferences** dialog with a full `set`. Fields the dialog does not know about are kept.

| Field | Type | Allowed values | Default | Notes |
| --- | --- | --- | --- | --- |
| `roles` | array of strings | | `[]` | Job titles. The listings task fails the search if this is missing or empty. |
| `locations` | array of strings | | `[]` | |
| `remoteOk` | boolean | | `false` | |
| `level` | string | `any`, `entry`, `mid`, `senior`, `lead` | `any` | Unknown values are shown as `any` in the dialog. |
| `salaryMin` | number or null | 0 or more | `null` | Applied only when a posting shows a salary. |
| `salaryCurrency` | string | up to 3 chars, stored uppercase | `""` | |
| `includeKeywords` | array of strings | | `[]` | Preferred terms. |
| `excludeKeywords` | array of strings | | `[]` | Postings mentioning these are dropped. |
| `excludeCompanies` | array of strings | | `[]` | |
| `maxPerDay` | number | integer 1 to 50 | `10` | |
| `updatedAt` | Timestamp | | | Set on every save. |
| `lastUpdate` | Date | | | Set on every save. |

The dialog splits comma-separated input into the arrays, trims each entry, drops empty entries and removes duplicates. The page treats preferences as "not set" until at least one of `roles`, `locations`, `includeKeywords`, `excludeKeywords` or `excludeCompanies` has an entry, and shows a **Set preferences** prompt until then. **Find jobs now** is disabled while preferences are not set.

```json
  "salaryCurrency": "USD",
  "includeKeywords": ["React", "TypeScript"],
  "excludeKeywords": ["night shift"],
  "excludeCompanies": [],
  "maxPerDay": 10,
  "updatedAt": "2026-10-12T02:15:00.000Z",
  "lastUpdate": "2026-10-12"
}
```

## settings/schedule

One document that controls which tasks each hourly run performs. The page's **Schedule** dialog writes it with a `set` that merges over the stored document, so fields the dialog does not show (such as `routineUrl`) survive a save. The routine reads it at the start of every run. If the document or a field is missing, both the page and the routine use the defaults below.

| Field | Type | Allowed values | Default | Written by | Notes |
| --- | --- | --- | --- | --- | --- |
| `timezone` | string | IANA time zone name | `Asia/Shanghai` | page | The dialog offers a fixed list of common zones, plus the stored value if it is not in the list. |
| `updatesEnabled` | boolean | | `true` | page | Turns reply checks on or off. |
| `updatesFrom` | number | integer 0 to 23 | `8` | page | First hour of the reply-check window. |
| `updatesTo` | number | integer 0 to 23 | `23` | page | Last hour of the window, inclusive. If `updatesFrom` is greater than `updatesTo`, the window wraps past midnight. If they are equal, replies are checked once a day at that hour. |
| `listingsEnabled` | boolean | | `true` | page | Turns the daily listings search on or off. A pending search request runs regardless. |
| `listingsHour` | number | integer 0 to 23 | `8` | page | Hour of the daily listings search. |
| `summaryEnabled` | boolean | | `true` | page | Turns the summary email on or off. |
| `summaryHour` | number | integer 0 to 23 | `21` | page | Hour of the summary email. |
| `importEnabled` | boolean | | `true` | page | Turns the email import on or off. The import runs only inside the reply-check window set by `updatesEnabled`, `updatesFrom` and `updatesTo`. |
| `updatedAt` | Timestamp | | | page | Set on every save. |
| `routineUrl` | string | `https` URL | | owner or Claude | The claude.ai URL of the routine. Not shown in the dialog. When it is set and a search request is pending, the page shows a **Run it now on claude.ai** link to it. Non-`https` values are ignored. |

All hours are whole hours in `timezone`. A non-integer or out-of-range hour is treated as the default. The page shows the current schedule under its title, for example "Replies hourly 8 AM–11 PM · Listings 8 AM · Summary 9 PM (Asia/Shanghai)".

### Example

```json
{
  "timezone": "Asia/Manila",
  "updatesEnabled": true,
  "updatesFrom": 8,
  "updatesTo": 23,
  "listingsEnabled": true,
  "listingsHour": 8,
  "summaryEnabled": true,
  "summaryHour": 21,
  "importEnabled": true,
  "updatedAt": "2026-10-12T02:20:00.000Z",
  "routineUrl": "<YOUR_ROUTINE_URL>"
}
```

## settings/searchRequest

One document holding the latest **Find jobs now** request and the result of the latest listings run. The page creates a request; the routine's listings task moves it through its statuses. The listings task also writes its result here at the end of every listings run, including the scheduled daily search when no request was made, so the page always shows the latest search.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `status` | string | `pending`, `running`, `done`, `failed` | page (`pending`), routine (the rest) | See the lifecycle below. |
| `requestedAt` | Timestamp | | page | When you selected **Find jobs now**. The routine keeps it as it is. |
| `startedAt` | Timestamp | | routine | When the listings task picked the request up. Set only for requested runs. |
| `finishedAt` | Timestamp | | routine | When the listings run ended. |
| `added` | number | integer 0 or more | routine | Number of new listings added. |
| `message` | string | short text | routine | One short sentence, for example "Added 4 new listings" or "No new matches; 6 near misses below", or the reason on `failed`. The page shows it after the result line. |
| `report` | object | see [report](#report) | routine | Details of the run. Written on every listings run that gets as far as searching. |

### report

| Field | Type | Notes |
| --- | --- | --- |
| `sources` | array of objects | One entry per source tried. See below. |
| `found` | number | Candidates found across all sources. |
| `added` | number | Candidates added as listings. If missing, the page uses the top-level `added`. |
| `duplicates` | number | Candidates already in the tracker (including skipped jobs) or repeated within the run. Shown as "Already tracked". |
| `closed` | number | Postings that are closed, removed or no longer accepting applications. |
| `old` | number | Postings more than 7 days old. Shown as "Too old". |
| `mismatched` | number | Postings that failed a preference rule (level, location, excluded keyword or company, salary below the floor). Shown as "Didn't match". |
| `nearMisses` | array of objects | Up to 15 close calls. See below. |

The page shows Found and Added always, and the other counts only when they are above zero. Missing or invalid counts are shown as 0. There is no count for unverified candidates; they appear only as near misses.

Each entry in `sources`:

| Field | Type | Allowed values | Notes |
| --- | --- | --- | --- |
| `name` | string | | Source name, for example `OnlineJobs.ph`, `Remotive`, `Himalayas` or `Web search`. Entries without a name are ignored. |
| `status` | string | `ok`, `empty`, `blocked`, `error` | `blocked` means HTTP 401, 403 or 429, a captcha, or a DNS failure. The page shows no label for `ok` and labels the others No results, Blocked and Error. Unknown values show no label. |
| `found` | number | integer 0 or more | Candidates from this source. |
| `note` | string | short text | Shown for `blocked` and `error` sources, for example "HTTP 403". |

Each entry in `nearMisses`:

| Field | Type | Notes |
| --- | --- | --- |
| `company` | string | Entries with neither a company nor a role are ignored. |
| `role` | string | |
| `location` | string | |
| `url` | string | Posting URL. The page shows a **View** link only for `http` and `https` URLs. |
| `source` | string | Where it was found. |
| `salary` | string | As posted, or empty. |
| `datePosted` | Date | Optional. Ignored by the page unless it is a valid `YYYY-MM-DD` date. |
| `match` | number or null | 0 to 100. The page clamps it to that range. |
| `reason` | string | One short phrase on why it was not added, for example "Posted 34 days ago", "Part-time", "Salary below 30,000 PHP" or "Couldn't open to confirm it is still open". |

Near misses are candidates that were old but posted within the last 60 days, mismatched on one rule only, or unverified (the posting could not be opened but the search result names a company, role and direct posting URL). Duplicates and closed jobs are never near misses.

**Add to Listings** on a near miss creates an `applications` document with the near miss's `company`, `role`, `location`, `url`, `source`, `salary`, `datePosted` (or `null`) and `match`, plus `fit` `Near miss: <reason>` (or `Near miss: flagged by the search` when there is no reason), `status` `listing`, `history` `[]`, `dateFound` and `lastUpdate` today, and `addedBy` `user`. The button is replaced by "Already in your tracker (<status>)" when the near miss duplicates a tracked job, or by "Added" when that job's `fit` starts with `Near miss: `.

### Lifecycle

1. **Find jobs now** replaces the whole document with `{ status: "pending", requestedAt }`, clearing any earlier result and report.
2. At the next hourly run (or when you select **Run now** on the routine page), the listings task sets `status` to `running` and `startedAt`.
3. The task ends by setting `status` to `done` with `finishedAt`, `added`, `message` and `report`. It sets `failed` only if every source failed or an unrecoverable error occurred. If no job titles are saved, it marks a pending request `failed` with "Set your search preferences first" and writes no report.
4. A scheduled daily search with no request writes the same result fields, so `status` becomes `done` (or `failed`) and the report is replaced.

Writes are pinned to the document version; on a version mismatch the routine re-reads and retries once.

Stuck requests: the routine treats a `running` request whose `startedAt` is more than 2 hours old as pending again. The page re-enables **Find jobs now** when a `pending` or `running` request's `requestedAt` is more than 2 hours old.

The page shows a progress bar under **Find jobs now** while a request is being sent, pending or running (and not stale), and a toast when the status changes to `done` or `failed` while it is open. It shows the **Last search** block whenever `status` is `done` or `failed` and a `report` object is present.

## settings/emailImport

One document holding how far the import task has scanned your Gmail and the result of its latest run. Only the routine writes it. The page reads it to show a status line under the **Import applications from email** toggle in the **Schedule** dialog, for example "Last scan 2h ago: 2 added, 1 moved from Listings", or "Not run yet" when the document is missing.

| Field | Type | Written by | Notes |
| --- | --- | --- | --- |
| `lastScanAt` | Timestamp | import task | Time of the last run whose Gmail search succeeded. The next scan searches from 1 hour before this time; the overlap is safe because the task skips emails it already imported. When it is missing (first run), the task searches the last 21 days. If the Gmail search fails, the task keeps the old value. |
| `lastResult` | object | import task | Counts from the latest run, written on every run. See below. |

`lastResult` fields:

| Field | Type | Notes |
| --- | --- | --- |
| `at` | Timestamp | When the run happened. |
| `emails` | number | Confirmation emails found in the search window. |
| `added` | number | New jobs created in `applied`. |
| `movedToApplied` | number | Existing `listing` or `skipped` jobs moved to `applied`. |
| `alreadyTracked` | number | Emails that matched a job already in `applied` or a later status. Their status was not changed. |
| `unreadable` | number | Emails skipped because the company or role could not be read clearly. |

Writes are pinned to the document version; on a version mismatch the routine re-reads and retries once.

### Example

```json
{
  "lastScanAt": "2026-10-12T05:02:14Z",
  "lastResult": {
    "at": "2026-10-12T05:02:14Z",
    "emails": 4,
    "added": 2,
    "movedToApplied": 1,
    "alreadyTracked": 1,
    "unreadable": 0
  }
}
```
