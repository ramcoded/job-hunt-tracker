# Data model

This document describes the data the tracker stores in its claude.ai Artifact database: the `applications` and `notifications` collections and the `settings/preferences`, `settings/schedule` and `settings/searchRequest` documents. For each one it lists every field, its type, its allowed values, and which part of the system reads or writes it (the page in `app/index.html`, or the hourly routine in `routines/hourly-check.md`).

## Overview

The database is the Artifact's built-in document store. The page opens it with `window.claude.use("db")` and listens for live changes with `onSnapshot`, so edits made by the routine appear on the page without a reload. The routine reads and writes it with the `ArtifactData` tool, acting as the artifact's owner.

| Path | Kind | Purpose |
| --- | --- | --- |
| `applications/<id>` | collection of documents | One document per job: listings, applications and skipped jobs. |
| `notifications/<id>` | collection of documents | Messages shown under the bell. |
| `settings/preferences` | single document | Search preferences for the listings task. |
| `settings/schedule` | single document | When the routine runs each task, plus the routine's URL. |
| `settings/searchRequest` | single document | The state of the latest **Find jobs now** request. |

In this document, "listings task", "reply checks" and "summary task" are the three tasks inside the hourly routine. See [Routines](routines.md).

Dates come in two formats:

- Date: `YYYY-MM-DD` string. The page uses the browser's local date. The routine uses the date in the `timezone` from `settings/schedule`.
- Timestamp: ISO 8601 string in UTC, for example `2026-10-12T01:30:00Z`.

## applications

Document IDs are generated by the database when the page adds a job (`col.add`) or when the listings task creates documents in a batch.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `company` | string | up to 120 chars in the form | page, listings task | Shown as "Untitled" when empty. |
| `role` | string | up to 160 chars in the form | page, listings task | |
| `location` | string | up to 120 chars in the form | page, listings task | |
| `url` | string | `http` or `https` URL | page, listings task | Other schemes are ignored by the page: no link is shown and Apply does not open anything. |
| `source` | string | up to 60 chars in the form | page, listings task | Where the posting was found, such as a job board name. |
| `salary` | string | free text, up to 60 chars in the form | page, listings task | As posted. Empty when not posted. |
| `match` | number or null | 0 to 100 | page, listings task | Fit estimate. The page clamps form input to 0-100 and stores `null` when empty. |
| `fit` | string | up to 600 chars in the form | page, listings task | One or two sentences on why the job fits. |
| `contact` | string | up to 160 chars in the form | page | Recruiter name or email. Reply checks use it to search Gmail. |
| `notes` | string | up to 4000 chars in the form | page, reply checks | Reply checks prepend one dated line per reply and keep the rest. |
| `status` | string | see [Statuses](#statuses) | page, reply checks, listings task | |
| `history` | array of objects | `{ status: string, date: Date }` | page, reply checks, listings task | One entry appended per status change. The listings task creates it as `[]`. |
| `dateFound` | Date | | page, listings task | Set when the job is added. Shown as "Added" on listing cards. Listings are sorted newest first by this field. |
| `datePosted` | Date or null | | page, listings task | Optional. The date shown on the original posting. The listings task omits it when the posting shows no date; the edit form stores `null` when empty. Shown as "Posted" on listing cards, and used as the second sort key. |
| `dateApplied` | Date or null | | page | Set to today when the job moves to `applied`, but only if it is empty. Editable in the form. Reply checks read it to set the start of their Gmail search, and the summary task reads it for "applied today" and follow-ups. |
| `followedUp` | Date | | page | Set by **Mark followed up**. Clears the follow-up reminder. Not shown in the edit form. |
| `lastUpdate` | Date | | page, all writers | Set on every write. Used as the last sort key. |
| `addedBy` | string | `user`, `claude` | page (`user`), listings task (`claude`) | The summary task counts only `claude` listings as "new listings added today". |
| `lastEmailCheck` | Timestamp | | reply checks | Time of the last Gmail check for this job. The next check searches from the later of this and `dateApplied`. |

### Statuses

| Value | Label on the page | Where it appears | Set by |
| --- | --- | --- | --- |
| `listing` | Listing | Listings tab | listings task, page (Add job, Restore) |
| `applied` | Applied | Applied tab | page (Apply, status picker) |
| `responded` | Responded | Applied tab | page, reply checks |
| `interview` | Interview | Applied tab | page, reply checks |
| `offer` | Offer | Applied tab | page, reply checks |
| `rejected` | Rejected | Applied tab | page, reply checks |
| `ghosted` | No reply | Applied tab | page (status picker, **No reply** button on a follow-up) |
| `skipped` | Skipped | Skipped drawer | page (Skip) |

Legacy value: `found` is read as `listing`. A document with a missing or `found` status is shown as a listing. The page does not rewrite the stored value until the job is next changed.

Rules the page applies:

- The status picker in the Applied tab offers only `applied`, `responded`, `interview`, `offer`, `rejected` and `ghosted`. To move a job back to `listing` or to `skipped`, use the edit form.
- Moving a job to `applied`, whether with **Apply**, the status picker or the edit form, sets `dateApplied` to today only if it is empty. An existing `dateApplied` is never overwritten.
- **Undo** after Apply or Skip restores the previous `status` and `dateApplied` and removes the last `history` entry if it matches.
- A job counts as "applied" in the pipeline if its status is `applied`, `responded`, `interview`, `offer`, `rejected` or `ghosted`.
- A job counts as "responded" in the pipeline if its current status or any `history` entry is `responded`, `interview`, `offer` or `rejected`. "Interview" counts `interview` or `offer`. "Offer" counts `offer`. The response rate is responded divided by applied.
- A follow-up is due when `status` is `applied`, `followedUp` is not set, and `dateApplied` is 7 or more days ago.
- Listing cards are sorted by `dateFound`, then `datePosted`, then `lastUpdate`, newest first.

The summary task uses the same "applied", "responded" and response rate definitions, and reports the follow-ups the page shows as due as "overdue". It also lists follow-ups due tomorrow: the same conditions with `dateApplied` exactly 6 days ago.

Reply checks cover jobs in `applied`, `responded`, `interview` and `ghosted`, so a reply to a job marked No reply moves it to `responded`, `interview`, `offer` or `rejected`. They never move a job backwards, for example from `interview` to `responded`.

### Example

```json
{
  "company": "Example Corp",
  "role": "Frontend Developer",
  "location": "Remote",
  "url": "https://jobs.example.com/frontend-developer",
  "source": "Company site",
  "salary": "",
  "match": 82,
  "fit": "React and TypeScript role at your level, fully remote.",
  "contact": "",
  "notes": "",
  "status": "applied",
  "history": [{ "status": "applied", "date": "2026-10-05" }],
  "dateFound": "2026-10-04",
  "datePosted": "2026-10-02",
  "dateApplied": "2026-10-05",
  "lastUpdate": "2026-10-05",
  "addedBy": "claude",
  "lastEmailCheck": "2026-10-12T01:00:00Z"
}
```

## notifications

The routine creates notifications. The page only marks them read.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `type` | string | `listing`, `reply`, `summary`, `status`, `info` | routine | Shown as "New listing", "Reply", "Daily summary", "Status change", "Update". The current routine writes only `listing`, `reply` and `summary`. Unknown values show as "Update". |
| `text` | string | one sentence | routine | Shown as the notification text. |
| `jobId` | string | an `applications` document ID | reply checks | Optional. When set, selecting the notification jumps to that job. |
| `createdAt` | Timestamp | | routine | Used for sorting and the "2h ago" label. |
| `read` | boolean | | routine (`false`), page (`true`) | Unread notifications count toward the bell badge. |
| `lastUpdate` | Date | | page | Set when the page marks the notification read. |

Document IDs: reply checks use IDs like `reply-<jobId>-<yyyymmddhhmm>`. The listings and summary tasks let the database generate them.

The bell shows all unread notifications under **New** and the 30 most recent read ones under **Earlier**. The badge counts unread notifications plus follow-ups due.

## settings/preferences

One document, written by the page's **Preferences** dialog with a full `set`. Fields the dialog does not know about are kept.

| Field | Type | Allowed values | Default | Notes |
| --- | --- | --- | --- | --- |
| `roles` | array of strings | | `[]` | Job titles. The listings task fails the search if this is missing or empty. |
| `locations` | array of strings | | `[]` | |
| `remoteOk` | boolean | | `false` | |
| `level` | string | `any`, `entry`, `mid`, `senior`, `lead` | `any` | Unknown values are shown as `any` in the dialog. |
| `salaryMin` | number or null | 0 or more | `null` | Applied only when a posting shows a salary. |
| `salaryCurrency` | string | up to 3 chars, stored uppercase | `""` | |
| `includeKeywords` | array of strings | | `[]` | Preferred terms. |
| `excludeKeywords` | array of strings | | `[]` | Postings mentioning these are dropped. |
| `excludeCompanies` | array of strings | | `[]` | |
| `maxPerDay` | number | integer 1 to 50 | `10` | |
| `updatedAt` | Timestamp | | | Set on every save. |
| `lastUpdate` | Date | | | Set on every save. |

The dialog splits comma-separated input into the arrays, trims each entry, drops empty entries and removes duplicates. The page treats preferences as "not set" until at least one of `roles`, `locations`, `includeKeywords`, `excludeKeywords` or `excludeCompanies` has an entry, and shows a **Set preferences** prompt until then. **Find jobs now** is disabled while preferences are not set.

### Example

```json
{
  "roles": ["Frontend Developer", "UI Engineer"],
  "locations": ["Manila"],
  "remoteOk": true,
  "level": "mid",
  "salaryMin": 60000,
  "salaryCurrency": "USD",
  "includeKeywords": ["React", "TypeScript"],
  "excludeKeywords": ["night shift"],
  "excludeCompanies": [],
  "maxPerDay": 10,
  "updatedAt": "2026-10-12T02:15:00.000Z",
  "lastUpdate": "2026-10-12"
}
```

## settings/schedule

One document that controls which tasks each hourly run performs. The page's **Schedule** dialog writes it with a `set` that merges over the stored document, so fields the dialog does not show (such as `routineUrl`) survive a save. The routine reads it at the start of every run. If the document or a field is missing, both the page and the routine use the defaults below.

| Field | Type | Allowed values | Default | Written by | Notes |
| --- | --- | --- | --- | --- | --- |
| `timezone` | string | IANA time zone name | `Asia/Shanghai` | page | The dialog offers a fixed list of common zones, plus the stored value if it is not in the list. |
| `updatesEnabled` | boolean | | `true` | page | Turns reply checks on or off. |
| `updatesFrom` | number | integer 0 to 23 | `8` | page | First hour of the reply-check window. |
| `updatesTo` | number | integer 0 to 23 | `23` | page | Last hour of the window, inclusive. If `updatesFrom` is greater than `updatesTo`, the window wraps past midnight. If they are equal, replies are checked once a day at that hour. |
| `listingsEnabled` | boolean | | `true` | page | Turns the daily listings search on or off. A pending search request runs regardless. |
| `listingsHour` | number | integer 0 to 23 | `8` | page | Hour of the daily listings search. |
| `summaryEnabled` | boolean | | `true` | page | Turns the summary email on or off. |
| `summaryHour` | number | integer 0 to 23 | `21` | page | Hour of the summary email. |
| `updatedAt` | Timestamp | | | page | Set on every save. |
| `routineUrl` | string | `https` URL | | owner or Claude | The claude.ai URL of the routine. Not shown in the dialog. When it is set and a search request is pending, the page shows a **Run it now on claude.ai** link to it. Non-`https` values are ignored. |

All hours are whole hours in `timezone`. A non-integer or out-of-range hour is treated as the default. The page shows the current schedule under its title, for example "Replies hourly 8 AM–11 PM · Listings 8 AM · Summary 9 PM (Asia/Shanghai)".

### Example

```json
{
  "timezone": "Asia/Manila",
  "updatesEnabled": true,
  "updatesFrom": 8,
  "updatesTo": 23,
  "listingsEnabled": true,
  "listingsHour": 8,
  "summaryEnabled": true,
  "summaryHour": 21,
  "updatedAt": "2026-10-12T02:20:00.000Z",
  "routineUrl": "<YOUR_ROUTINE_URL>"
}
```

## settings/searchRequest

One document holding the latest **Find jobs now** request. The page creates it; the routine's listings task moves it through its statuses.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `status` | string | `pending`, `running`, `done`, `failed` | page (`pending`), routine (the rest) | See the lifecycle below. |
| `requestedAt` | Timestamp | | page | When you selected **Find jobs now**. |
| `startedAt` | Timestamp | | routine | When the listings task picked the request up. |
| `finishedAt` | Timestamp | | routine | When the search ended, on `done`. |
| `added` | number | integer 0 or more | routine | Number of new listings added, on `done`. |
| `message` | string | short text | routine | A short note on `done` (for example "No new matches found"), or the reason on `failed`. The page shows the reason for a failed search. |

Lifecycle:

1. **Find jobs now** replaces the whole document with `{ status: "pending", requestedAt }`, clearing any earlier result.
2. At the next hourly run (or when you select **Run now** on the routine page), the listings task sets `status` to `running` and `startedAt`.
3. The task ends by setting `status` to `done` with `finishedAt`, `added` and `message`, or to `failed` with `message`. A search fails, for example, when no job titles are saved ("Set your search preferences first") or when the routine cannot open job sites.

Stuck requests: the routine treats a `running` request whose `startedAt` is more than 2 hours old as pending again. The page re-enables **Find jobs now** when a `pending` or `running` request's `requestedAt` is more than 2 hours old.

The page shows a toast when the status changes to `done` or `failed` while it is open.

### Example

```json
{
  "status": "done",
  "requestedAt": "2026-10-12T03:00:00.000Z",
  "startedAt": "2026-10-12T03:04:10Z",
  "finishedAt": "2026-10-12T03:09:45Z",
  "added": 4,
  "message": "4 new listings added"
}
```
