# Data model

This document describes the data the tracker stores in its claude.ai Artifact database: the `applications` and `notifications` collections and the `settings/preferences` document. For each one it lists every field, its type, its allowed values, and which part of the system reads or writes it (the page in `app/index.html`, or the routines in `routines/`).

## Overview

The database is the Artifact's built-in document store. The page opens it with `window.claude.use("db")` and listens for live changes with `onSnapshot`, so edits made by a routine appear on the page without a reload. The routines read and write it with the `ArtifactData` tool, acting as the artifact's owner.

| Path | Kind | Purpose |
| --- | --- | --- |
| `applications/<id>` | collection of documents | One document per job: listings, applications and skipped jobs. |
| `notifications/<id>` | collection of documents | Messages shown under the bell. |
| `settings/preferences` | single document | Search preferences for the daily listings routine. |

Dates come in two formats:

- Date: `YYYY-MM-DD` string. The page uses the browser's local date. The routines use the date in Asia/Shanghai.
- Timestamp: ISO 8601 string in UTC, for example `2026-10-12T01:30:00Z`.

## applications

Document IDs are generated by the database when the page adds a job (`col.add`) or by the daily listings routine when it creates documents in a batch.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `company` | string | up to 120 chars in the form | page, listings routine | Shown as "Untitled" when empty. |
| `role` | string | up to 160 chars in the form | page, listings routine | |
| `location` | string | up to 120 chars in the form | page, listings routine | |
| `url` | string | `http` or `https` URL | page, listings routine | Other schemes are ignored by the page: no link is shown and Apply does not open anything. |
| `source` | string | up to 60 chars in the form | page, listings routine | Where the posting was found, such as a job board name. |
| `salary` | string | free text, up to 60 chars in the form | page, listings routine | As posted. Empty when not posted. |
| `match` | number or null | 0 to 100 | page, listings routine | Fit estimate. The page clamps form input to 0-100 and stores `null` when empty. |
| `fit` | string | up to 600 chars in the form | page, listings routine | One or two sentences on why the job fits. |
| `contact` | string | up to 160 chars in the form | page | Recruiter name or email. The updates routine uses it to search Gmail. |
| `notes` | string | up to 4000 chars in the form | page, updates routine | The updates routine prepends one dated line per reply and keeps the rest. |
| `status` | string | see [Statuses](#statuses) | page, updates routine, listings routine | |
| `history` | array of objects | `{ status: string, date: Date }` | page, updates routine, listings routine | One entry appended per status change. The listings routine creates it as `[]`. |
| `dateFound` | Date | | page, listings routine | Set when the job is added. Listings are sorted newest first by this field. |
| `dateApplied` | Date or null | | page | Set to today when the job moves to `applied`. Editable in the form. The updates routine reads it to set the start of its Gmail search, and the summary routine reads it for "applied today" and follow-ups. |
| `followedUp` | Date | | page | Set by **Mark followed up**. Clears the follow-up reminder. Not shown in the edit form. |
| `lastUpdate` | Date | | page, all writers | Set on every write. Used as a secondary sort key. |
| `addedBy` | string | `user`, `claude` | page (`user`), listings routine (`claude`) | The summary routine counts only `claude` listings as "new listings added today". |
| `lastEmailCheck` | Timestamp | | updates routine | Time of the last Gmail check for this job. The next check searches from the later of this and `dateApplied`. |

### Statuses

| Value | Label on the page | Where it appears | Set by |
| --- | --- | --- | --- |
| `listing` | Listing | Listings tab | listings routine, page (Add job, Restore) |
| `applied` | Applied | Applied tab | page (Apply, status picker) |
| `responded` | Responded | Applied tab | page, updates routine |
| `interview` | Interview | Applied tab | page, updates routine |
| `offer` | Offer | Applied tab | page, updates routine |
| `rejected` | Rejected | Applied tab | page, updates routine |
| `ghosted` | No reply | Applied tab | page (status picker, **No reply** button on a follow-up) |
| `skipped` | Skipped | Skipped drawer | page (Skip) |

Legacy value: `found` is read as `listing`. A document with a missing or `found` status is shown as a listing. The page does not rewrite the stored value until the job is next changed.

Rules the page applies:

- The status picker in the Applied tab offers only `applied`, `responded`, `interview`, `offer`, `rejected` and `ghosted`. To move a job back to `listing` or to `skipped`, use the edit form.
- Moving a job to `applied` with **Apply** always sets `dateApplied` to today. Changing the status to `applied` in the status picker or edit form sets `dateApplied` only if it is empty.
- **Undo** after Apply or Skip restores the previous `status` and `dateApplied` and removes the last `history` entry if it matches.
- A job counts as "applied" in the pipeline if its status is `applied`, `responded`, `interview`, `offer`, `rejected` or `ghosted`.
- A job counts as "responded" in the pipeline if its current status or any `history` entry is `responded`, `interview`, `offer` or `rejected`. "Interview" counts `interview` or `offer`. "Offer" counts `offer`. The response rate is responded divided by applied.
- A follow-up is due when `status` is `applied`, `followedUp` is not set, and `dateApplied` is 7 or more days ago.

The daily summary routine uses the same "applied", "responded" and response rate definitions, and reports the follow-ups the page shows as due as "overdue". It also lists follow-ups due tomorrow: the same conditions with `dateApplied` exactly 6 days ago.

The updates routine checks jobs in `applied`, `responded`, `interview` and `ghosted`, so a reply to a job marked No reply moves it to `responded`, `interview`, `offer` or `rejected`. It never moves a job backwards, for example from `interview` to `responded`.

### Example

```json
{
  "company": "Example Corp",
  "role": "Frontend Developer",
  "location": "Remote",
  "url": "https://jobs.example.com/frontend-developer",
  "source": "Company site",
  "salary": "",
  "match": 82,
  "fit": "React and TypeScript role at your level, fully remote.",
  "contact": "",
  "notes": "",
  "status": "applied",
  "history": [{ "status": "applied", "date": "2026-10-05" }],
  "dateFound": "2026-10-04",
  "dateApplied": "2026-10-05",
  "lastUpdate": "2026-10-05",
  "addedBy": "claude",
  "lastEmailCheck": "2026-10-12T01:00:00Z"
}
```

## notifications

Routines create notifications. The page only marks them read.

| Field | Type | Allowed values | Written by | Notes |
| --- | --- | --- | --- | --- |
| `type` | string | `listing`, `reply`, `summary`, `status`, `info` | routines | Shown as "New listing", "Reply", "Daily summary", "Status change", "Update". The current routines write only `listing`, `reply` and `summary`. Unknown values show as "Update". |
| `text` | string | one sentence | routines | Shown as the notification text. |
| `jobId` | string | an `applications` document ID | updates routine | Optional. When set, selecting the notification jumps to that job. |
| `createdAt` | Timestamp | | routines | Used for sorting and the "2h ago" label. |
| `read` | boolean | | routines (`false`), page (`true`) | Unread notifications count toward the bell badge. |
| `lastUpdate` | Date | | page | Set when the page marks the notification read. |

Document IDs: the updates routine uses IDs like `reply-<jobId>-<yyyymmddhhmm>`. Other routines let the database generate them.

The bell shows all unread notifications under **New** and the 30 most recent read ones under **Earlier**. The badge counts unread notifications plus follow-ups due.

## settings/preferences

One document, written by the page's **Preferences** dialog with a full `set`. Fields the dialog does not know about are kept.

| Field | Type | Allowed values | Default | Notes |
| --- | --- | --- | --- | --- |
| `roles` | array of strings | | `[]` | Job titles. The listings routine stops if this is missing or empty. |
| `locations` | array of strings | | `[]` | |
| `remoteOk` | boolean | | `false` | |
| `level` | string | `any`, `entry`, `mid`, `senior`, `lead` | `any` | Unknown values are shown as `any` in the dialog. |
| `salaryMin` | number or null | 0 or more | `null` | Applied only when a posting shows a salary. |
| `salaryCurrency` | string | up to 3 chars, stored uppercase | `""` | |
| `includeKeywords` | array of strings | | `[]` | Preferred terms. |
| `excludeKeywords` | array of strings | | `[]` | Postings mentioning these are dropped. |
| `excludeCompanies` | array of strings | | `[]` | |
| `maxPerDay` | number | integer 1 to 50 | `10` | |
| `updatedAt` | Timestamp | | | Set on every save. |
| `lastUpdate` | Date | | | Set on every save. |

The dialog splits comma-separated input into the arrays, trims each entry, drops empty entries and removes duplicates. The page treats preferences as "not set" until at least one of `roles`, `locations`, `includeKeywords`, `excludeKeywords` or `excludeCompanies` has an entry, and shows a **Set preferences** prompt until then.

### Example

```json
{
  "roles": ["Frontend Developer", "UI Engineer"],
  "locations": ["Manila"],
  "remoteOk": true,
  "level": "mid",
  "salaryMin": 60000,
  "salaryCurrency": "USD",
  "includeKeywords": ["React", "TypeScript"],
  "excludeKeywords": ["night shift"],
  "excludeCompanies": [],
  "maxPerDay": 10,
  "updatedAt": "2026-10-12T02:15:00.000Z",
  "lastUpdate": "2026-10-12"
}
```
